WHAT TO SAY: Since no natural condition gave adaptation a reason to exist, we built one: a server that is normal for 8 seconds, then switches on a cap, where too many connections hurts. Now the best setting really changes in the middle of the download. A very simple controller handled it well. We call it the drop rule: it watches how fast each request goes, and the first time that speed falls below half of its best, it switches once to fewer connections. It took 58.7 seconds against 76.7 for the best of the fixed settings we ran: 23.4 % less time, in all 10 rounds. Reducing the number of connections did almost all the work; changing piece size alone made it worse. But aria2, which does not adapt at all, was still faster: 53.6 seconds. Finding out why changed our whole conclusion. We also tried a “workload selector” that watches the first seconds, guesses the kind of server, and picks a preset; across six server variants it matched the best fixed setting for each on average. IN SIMPLE WORDS: When there is a real reason to adapt, one simple rule is enough. But a tool that does not adapt still won. TERMS ON THIS SLIDE: • Connection cap: our server rule that gives each new connection less speed the more you already have. • Drop rule: “if request speed drops below half its best, switch once to a preset setting”. It only uses what it has seen so far. • N and S / N only / S only: versions that change both dials, only the number of connections, or only the piece size. • Round: one run of every option, in random order.
