WHAT TO SAY: To test fairly we wrote our own test server, so we know exactly how it behaves. It follows three rules. One: each response is sent at the speed that was in force when its request arrived, and keeps that speed. Two: the speed can change on a timetable. The left chart is our reference timetable: 640 KiB/s, a dip to 160 KiB/s between 2 and 4 seconds, then fast at 2,500 KiB/s. Three: we can switch on a “soft cap”, which gives each new connection less speed the more connections you already have. The right chart shows that past about three connections, the total speed actually goes down. So under the cap, too many connections hurts. We also add delay and packet loss with Linux tools, replay real mobile-network recordings, and check every downloaded file with SHA-256. SETUP DETAILS (if asked): client and server share one machine over loopback, left at the default MTU (65,536 bytes) with the default TCP congestion control (CUBIC); delay and loss are added with netem. The server’s pacing, not TCP, is the bottleneck here, and a loopback path is not a real path, which is why we added the real-server checks. “No cap” is the server without the connection throttle; its base schedule is 640 KiB/s for the first second, then 2500 KiB/s. IN SIMPLE WORDS: We built a “test track” where we control the weather, so we can see exactly why each result happens. The cap is the one place we deliberately created a reason to adapt. TERMS ON THIS SLIDE: • Paced server / timetable: a server that sends data at set speeds that change at set times. The “slow, then fast” timetable is our reference. • KiB/s, MiB/s: kibibytes or mebibytes per second; 1 MiB = 1,048,576 bytes. • Soft cap: our rule rate = min(base, C / (k(1 + γ(k − 1)))). C is the total budget (8 MiB/s), k the number of active requests including the new one, γ a small penalty for each extra connection. • Test scenarios used later: “no cap”, “cap from the start”, and “cap switching on at 8 seconds”. • tc netem: a Linux tool that adds delay and packet loss to a network link. Ours: 40 ms each way (80 ms round trip), 0.4 % loss. • Mahimahi: a tool that replays recorded mobile-network traces. • SHA-256: a fingerprint of a file; if it matches, the file is byte-for-byte correct.
