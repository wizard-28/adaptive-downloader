Five invariants

  1. One request fetches one contiguous range
  2. Ranges never resize in flight (except an opt-in split)
  3. A failed range retries with the same bounds
  4. Lowering N never cancels a request
  5. One decision at a time, each changing N or S, not both at once

Controllers: fixed settings, simple rules (such as “drop rule”), a workload selector, an online tuner, and learning agents (LinUCB, Double DQN)

WHAT TO SAY: Every controller, from the simplest fixed setting to the neural-network agent, plugs into the same small interface. It has two functions: choose an action, and learn from the result. Because they all use the same engine, comparisons between them are fair. The engine follows five rules. For example: a failed piece is retried with exactly the same byte range, and lowering N never kills a download that is already running; the extra worker just stops after its current piece. Two engine options matter later. Straggler splitting, shown in the diagram: near the end, connection A is still working on a big piece while connection B has nothing to do. B takes over the second half of what A has not yet received, so both finish sooner. We only split if at least 2 MiB remain, so each half is worth a new request. And we can switch off the old 30-second time limit per request. ON JOINT CONTROL (if asked): both N and S are adapted, but one dial per decision. The rule-based joint policy alternates between N and S; the causal drop controller and workload selector choose a target pair (N, S) together: N jumps to the target in one decision, then S moves one step (1 MiB) at a time, and N and S never change in the same decision; LinUCB and the joint DQN agent pick one of five single-dial actions, and the cap-trained DQN agents one of three (N only). A learner that picks the pair (N, S) as one action at a fixed interval, as in our first proposal, was not built. WHY THIS DIFFERS FROM OUR FIRST PROPOSAL (if asked): Review 1 described the idea. In the build, we changed how decisions are triggered and what one action does, for reasons we recorded: cleaner measurement, clean ablations, and early learning failures. Our reports should have said so. Decisions come after each finished request, not on a timer, because a request boundary is the clean moment to change N or S. Actions change one dial so we can compare N-only, S-only and joint, and because the early agents that learned S broke the file into tiny pieces. IN SIMPLE WORDS: One plug for every brain, and a few strict rules so the file always comes out correct. TERMS ON THIS SLIDE: • Interface: a contract in code; any controller that has these two functions can be plugged in. • Invariant: a rule the code always keeps true. • Half-open range [s, e): bytes from s up to but not including e. HTTP uses inclusive ranges, so we convert in exactly one place to avoid off-by-one bugs. • Straggler: a slow piece still downloading when everything else is done. Splitting it shares the remaining work. • Deadline / timeout: the maximum time a request may run before it is cancelled. • Race detector: Go’s tool that checks for bugs when many things run at once.
