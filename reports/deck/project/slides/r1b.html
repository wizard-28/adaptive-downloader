WHAT TO SAY: Is this just an aria2 quirk, or a quirk of one server timetable? We checked. The chart shows every paired run against aria2: the main benchmark, six different server speed timetables (slow then fast, a long slow dip, partial recovery, always fast, always slow), and a standard NGINX web server that we did not write, with two rate-limit settings. Below 1 means ours was faster. We were faster everywhere except the always-slow timetable, where the two were equal, which is exactly what you would expect when there is no speed change to exploit. We also tested two other popular tools, axel and lftp; the next slide shows them. And on the slow-then-fast server, ours was faster than aria2 in all nine combinations of network delay and packet loss we tried. But on a server that throttles connections (next section), all four tools finished in about 53 seconds: no winner. IN SIMPLE WORDS: Any tool that splits the file once at the start suffers on a server that speeds up later. When that timing effect is not there, everyone is roughly equal. TERMS ON THIS SLIDE: • Timetable: the server’s speed over time. • NGINX “rate limit”: NGINX’s standard setting that limits each response to a fixed speed; “first 1 MiB free” sends the first megabyte at full speed and limits the rest. • Delay × loss: we tried 10, 40 and 100 ms delay with 0, 0.4 and 2 % packet loss. • Quick checks (“screens”): small experiments to check a direction, not final proof. • wget2 was dropped because it uses one connection per file; IDM is Windows-only and closed, so we could not script it.
