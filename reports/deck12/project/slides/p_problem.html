WHAT TO SAY: Every parallel downloader has two dials. N is how many connections it opens at once. S is how big each piece of the file is. Tools like aria2, axel and lftp set both once, at the start, and never touch them again. But a real download meets changing conditions: the server speeds up or slows down, throttles you if you open too many connections, the network adds delay or loses packets, or a mobile link swings. The table shows what was done before, with sources, and what this study does. Balaprakash and colleagues (ICPP 2016) tuned the number of parallel streams on production science links with a direct-search method, against user default settings. Falcon (Arifuzzaman and Arslan, SC 2021; Arifuzzaman and colleagues, TPDS 2023) tunes concurrency with a utility score and online search, against Globus’s fixed settings and a tuner called HARP. FastBioDL (Swargo and colleagues, arXiv 2025) tunes the number of streams for genome downloads with a utility score and gradient descent, against the SRA tools and fixed settings of 3 and 5 streams. MDTP (Abdollah and colleagues, ICCCN 2025) shares one download across several servers and sizes the pieces per server, against aria2 in multi-server mode. DeLoad (Liu and colleagues, arXiv 2025) sizes download tasks for short-video preloading with deep reinforcement learning. In the papers we read, we did not find, together: a race against stock tools and the best fixed setting of the same program; a measurement of how much a perfect controller could gain before building one; a separation of the controller’s gain from engine effects such as request timeouts, splitting slow pieces and when requests start; or cases where adapting gave nothing. We read abstracts, and the full text only for FastBioDL, so this says what we found in what we read, not that nobody has done it. This study adapts both N and S, compares rule-based, bandit and deep-reinforcement-learning controllers with aria2, axel, lftp and the best fixed setting of our own engine, measures the ceiling first, separates engine effects, and keeps its negative results. Our objectives: first, does adapting N and S during the download beat aria2 and a well-chosen fixed setting when conditions are not ideal? Second, if there is a gain, does it come from adapting, or just from how the file is cut into pieces? Third, how much could a perfect controller gain, measured before we build any learning controller? Fourth, do our rule-based and learning controllers hold up, in controlled tests and on real servers? IN SIMPLE WORDS: Others asked how to tune the number of connections. We ask whether there is anything to tune, and where any gain really comes from. TERMS ON THIS SLIDE: • N: how many connections run at once. S: the size of each piece (a range of bytes). • aria2, axel, lftp: popular open-source download tools. • Fixed setting: the same N and S for the whole download. • Perfect controller (“oracle”): an imaginary controller that knows the future; it shows the most any real controller could gain. • Engine effects: behaviour of the downloading machinery itself, such as request timeouts and splitting slow pieces, as opposed to the controller that picks N and S. • Bandit and deep reinforcement learning: two ways for a controller to learn from a reward which action to take. • Utility, direct search, gradient descent: ways of improving a setting by trying changes and keeping the better ones.
