N: number of connections · S: size of each piece · fixed setting: the same N and S for the whole download

02

WHAT TO SAY: Every parallel downloader has two dials. N is how many connections it opens at once. S is how big each piece of the file is. Tools like aria2, axel and lftp set both once, at the start, and never touch them again. But a real download meets changing conditions: the server speeds up or slows down, throttles you if you open too many connections, the network adds delay or loses packets, or a mobile link swings. Earlier research tunes the number of connections while a transfer runs. In the papers we read, we did not find a race against the stock tools together with the best fixed setting of the same program, a measurement of how much a perfect controller could gain before building one, or a separation of the controller’s gain from engine effects. That is our problem statement. Our objectives: first, does adapting N and S during the download beat aria2 and a well-chosen fixed setting when conditions are not ideal? Second, if there is a gain, does it come from adapting, or just from how the file is cut into pieces? Third, how much could a perfect controller gain, measured before we build any learning controller? Fourth, do our rule-based and learning controllers hold up, in controlled tests and on real servers? IN SIMPLE WORDS: We ask whether changing the settings while a download runs actually makes it faster, and where any gain really comes from. TERMS ON THIS SLIDE: • N: how many connections run at once. S: the size of each piece (a range of bytes). • aria2, axel, lftp: popular open-source download tools. • Fixed setting: the same N and S for the whole download. • Perfect controller (“oracle”): an imaginary controller that knows the future; it shows the most any real controller could gain.
