WHAT TO SAY: What is new, and what is it good for? First, what is not new: other people have built downloaders that tune the number of connections, and download managers already split slow pieces. We do not claim a new algorithm. Our innovation is the way we answer the question. We measure the ceiling first: how much a perfect controller could gain, before we build any learning controller. We race every adaptive controller against aria2, axel, lftp and the best fixed setting of the same program. We separate engine effects from the controller, which showed that our big win over aria2 was mostly about when requests start, and that a request timeout and missing splitting of slow pieces explained aria2’s lead under the cap. We found a hidden server rule, that a request keeps the speed it started with, and tested it with a control server. And we kept our negative results, including tests on real servers. Applications: if you only want fast downloads from public mirrors, a simple fixed setting such as 8 connections of 1 MiB was on average 3.7 % slower than the best fixed setting for each case, so it is a strong default. If you plan to build an adaptive or learned controller, measure the ceiling first; on the mobile traces it would have saved only 0.41 %. And fix the downloader’s basics before adding intelligence. IN SIMPLE WORDS: Others asked how to tune it. We asked whether there is anything to tune, measured it carefully, and explained the answer. TERMS ON THIS SLIDE: • Ceiling (“headroom”): the most any controller could gain. • Engine effects: behaviour of the downloading machinery itself, such as request timeouts and splitting slow pieces. • Hidden server rule: on some servers a request runs at whatever speed was in force when it started. • Mirror: a server that hosts copies of files for anyone to download.
